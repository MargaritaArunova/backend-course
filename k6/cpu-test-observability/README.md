# Observability CPU Performance Testing

Тестирование производительности ObservabilityService при различных CPU лимитах с использованием K6.

## Описание

Этот набор тестов предназначен для:
1. Измерения производительности различных типов операций (контроллеры, репозитории, статистика)
2. Анализа влияния CPU лимитов (0.5 и 1.0 ядра) на время отклика
3. Сбора и анализа observability статистики из логов приложения
4. Визуализации зависимости метрик от количества CPU

## Компоненты

### 1. load-test.js
K6 тестовый скрипт, который выполняет различные типы операций:
- **Controller операции (50%)**: Чтение и запись через контроллеры
- **Self-Like Stats (20%)**: Тяжелые запросы к БД со статистикой
- **Like операции (15%)**: Операции с лайками (репозиторий)
- **Observability Stats (15%)**: Запросы к observability эндпоинтам

### 2. run-cpu-tests.sh
Bash скрипт для автоматизации тестирования:
- Изменяет CPU лимиты в Docker (0.5 и 1.0 ядра)
- Запускает K6 тесты
- Собирает логи приложения во время тестов
- Извлекает observability статистику из логов
- Сохраняет результаты в структурированном виде

### 3. analyze-results.py
Python скрипт для анализа и визуализации:
- Парсит JSON результаты K6
- Извлекает метрики из логов приложения
- Строит графики зависимости метрик от CPU
- Генерирует сводную статистику

### Конфигурация

Отредактируйте переменные в `run-cpu-tests.sh`:

```bash
REMOTE_HOST="marunova-backend"        # SSH хост
REMOTE_COMPOSE_DIR="~/backend-course" # Путь к проекту на сервере
BASE_URL="http://192.168.1.100:8080"  # URL приложения
VUS=50                                # Количество виртуальных пользователей
DURATION=2m                           # Длительность теста
```

## Использование

### 1. Запуск тестов

```bash
chmod +x run-cpu-tests.sh
./run-cpu-tests.sh
```

Скрипт автоматически:
- Переключит CPU лимиты между 0.5 и 1.0 ядрами
- Запустит K6 тесты для каждого лимита
- Соберет логи приложения
- Сохранит результаты в директорию `results/`

### 2. Анализ результатов

```bash
chmod +x analyze-results.py
./analyze-results.py
```

Скрипт сгенерирует:
- Графики в `results/graphs/`
- CSV файл со статистикой
- Вывод observability метрик в консоль

### 3. Ручной запуск K6 теста

```bash
k6 run \
  -e BASE_URL="http://localhost:8080" \
  -e VUS=50 \
  -e DURATION=2m \
  load-test.js
```

## Метрики

### K6 Метрики
- **controller_response_time**: Время отклика контроллеров
- **repository_response_time**: Время отклика операций с репозиторием
- **self_like_stats_response_time**: Время расчета статистики self-likes
- **observability_stats_response_time**: Время получения observability статистики
- **http_req_duration**: Общее время отклика HTTP запросов

### Observability Метрики (из логов)
- Статистика по каждому методу за 3 временных окна:
  - **SHORT** (10 секунд)
  - **MEDIUM** (30 секунд)
  - **LONG** (60 секунд)
- Для каждого метода:
  - Количество вызовов (count)
  - Среднее время (avg)
  - Минимальное время (min)
  - Максимальное время (max)

## Графики

### 1. P95 Response Time vs CPU Cores
Показывает зависимость 95-го перцентиля времени отклика от количества CPU для разных типов операций.

### 2. Mean Response Time vs CPU Cores
Показывает зависимость среднего времени отклика от количества CPU.

### 3. Overall Response Time vs CPU Cores
Сравнение P95 и среднего времени отклика для всех операций.

## Анализ результатов

После выполнения тестов обратите внимание на:

1. **Влияние CPU на производительность**
   - Как меняется время отклика при переходе с 0.5 на 1.0 ядро
   - Какие операции наиболее чувствительны к CPU

2. **Observability overhead**
   - Время выполнения методов observability
   - Влияние AOP аспектов на производительность

3. **Тяжелые операции**
   - Self-Like Stats - показывает производительность запросов к БД
   - Repository операции - показывает производительность JPA

4. **Внутренняя статистика**
   - Метрики из логов показывают реальное время выполнения методов
   - Сравнение с внешними K6 метриками

## Troubleshooting

### Приложение не запускается после изменения CPU
```bash
# Проверьте статус контейнера
ssh marunova-backend "docker ps -a"

# Проверьте логи
ssh marunova-backend "docker logs hl-module1-app"
```

### Нет данных в логах
- Увеличьте `DURATION` в скрипте (минимум 2 минуты)
- Проверьте уровень логирования в `application.properties`:
  ```properties
  logging.level.com.backend.course.observability=INFO
  ```

### K6 тесты завершаются с ошибками
- Убедитесь, что приложение доступно: `curl http://192.168.1.100:8080/users`
- Проверьте базу данных: она должна быть запущена и доступна
- Увеличьте таймауты в скрипте

## Интерпретация результатов

### Хорошие показатели
- P95 < 500ms для controller операций
- P95 < 1000ms для self-like stats
- Линейное улучшение при увеличении CPU

### Проблемные зоны
- P95 > 2000ms - узкое место в приложении
- Нет улучшения при увеличении CPU - I/O bound операции
- Высокий разброс (max >> p95) - нестабильная производительность
